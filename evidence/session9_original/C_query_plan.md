# Deliverable C — Spark Query-Plan & Shuffle Audit (`C_query_plan`)

- **Evidence File:** `evidence/session9/C_query_plan.txt` & `outputs/spark_runtime_evidence.json` (Apache Spark `3.5.7`).
- **Inspected Operation:** `enrich_windows()` & `aggregate_monoid()` in `traffic_data/spark_etl.py` joining `33,441` aggregated 30m GPS windows with `segments` (`84,633` rows), `vmax_lookup` (`84,633` rows), and `streets` (`5,553` rows), plus writing/reading `data/lakehouse/curated_gold` partitioned by `year_month`.

| Audit Check | Verified Evidence from `df.explain(True)` |
|---|---|
| **1. Which query or DataFrame operation did you inspect?** | `aggregate_monoid(events, salted=True, buckets=8)` followed by `enrich_windows(windows, segments, lookup, broadcast=True, streets=streets)` and `spark.read.parquet("data/lakehouse/curated_gold").filter("year_month = '2020-08'").select("segment_id", "date", "period", "LOS")`. |
| **2. Where is `Exchange` / shuffle visible?** | In Baseline (`SortMergeJoin`), `Exchange hashpartitioning(...)` appears **10 times** (shuffling both fact and dimension tables before `Sort`). In Optimized (`BroadcastHashJoin`), `Exchange` appears **only 2 times**: exclusively inside `HashAggregate` for the `5-Tuple Monoid` (`Exchange hashpartitioning(segment_id, date, period, 8)`). |
| **3. Which join strategy is used?** | **`BroadcastHashJoin [segment_id], BuildRight`** and **`BroadcastHashJoin [street_id], LeftOuter, BuildRight`** in the optimized pipeline (replacing 4 `SortMergeJoin` + `Sort` operators in the baseline plan). |
| **4. What determines partitioning at this point?** | `spark.sql.shuffle.partitions = 8` (tuned to match our 4-core local container budget without small-task scheduling overhead) and `hashpartitioning(segment_id, window_start, salt, 8)` during Stage-1 salted monoid aggregation, followed by `partitionBy("year_month")` (`10` monthly directories) on disk. |
| **5. Would `cache/persist` help? Why or why not?** | **Selective `persist(MEMORY_AND_DISK)` helps ONLY on `silver_cleaned_windows` and `train_events`** because they are reused across multiple downstream actions (`fit_velocity_lookup`, `Line-Graph PageRank`, `FPGrowth`, `7D K-Means`, `Random Forest`). Caching one-pass intermediate DataFrames wastes executor heap RAM (`10.5 GB` budget). |
| **6. Could `BroadcastHashJoin` help? Under what data-size condition?** | **Yes — verified:** `segments` (`84,633` rows, `~6.8 MB`) and `streets` (`5,553` rows, `~0.4 MB`) are well below `spark.sql.autoBroadcastJoinThreshold` (`10 MB` default), cutting `Exchange` stages from `10 -> 2` (`-80%`). It remains valid as long as static road topology fits comfortably in `< 100 MB` of executor broadcast memory. |
| **7. Is Parquet / data layout / partitioning helping the actual access pattern?** | **Yes — verified in `Physical Plan`:** `PartitionFilters: [isnotnull(year_month#751), (year_month#751 = 2020-08)]` skips `9/10` monthly directories on disk, and `ReadSchema: struct<segment_id:bigint,date:string,period:string,LOS:string>` reads only `4` of `26` columns via `ColumnarToRow`. |
